# Deviations from apron-server-go

Each entry names the behavior, how the Go server does it, how this port does
it, and why. A client-visible difference that is not listed here is a bug.
An entry marked *interim* is the state after a phase and goes away when the
named phase lands.

| Area | Go | Rust | Why |
|---|---|---|---|
| `server.agent` (§3.1) | `apron-go/9` | `apron-rust/9` | The agent names the implementation. Clients key nothing on it; `apron` carries the protocol version. |
| Display names (§3.3) | `normalizeName` applies the PRECIS Nickname profile (RFC 8266) through `golang.org/x/text/secure/precis`: NFKC normalization and the FreeformClass check, besides dropping invisible characters and folding spaces. | Drops Cc, Cf, Co, and Cs characters, maps Zs to space, collapses and trims spaces, and caps the name at 64 runes. No NFKC, no FreeformClass check: a name with compatibility characters such as fullwidth letters is kept as sent. | `x/text` is not Go's standard library, so rust-stdlib has no Unicode normalization. A third-party crate (`unicode-normalization`) would need an allowlist entry; the owner decides. |
| Push delivery (§4.9), *interim until the rust-stdlib transport fix* | A delivery to a push host whose idle keep-alive connection the host has closed dials a new connection and is delivered. | The pooled connection is reused, the POST fails with `EOF`, and the push is dropped (status 0): the registration is kept, but that push never arrives. | rust-stdlib's `net/http` transport passes a closed idle connection as healthy; docs/PORT.md, "Pending rust-stdlib fixes". Disabling keep-alives here would work around it, which AGENTS.md rules out. |
| WebSocket close handshake | coder/websocket's `Close` sends a close frame and waits up to 5 seconds for the peer's. | `close` sends the close frame and closes the TCP connection at once. | The server only ever uses `CloseNow` (no handshake) and `Close(1003)` on a binary frame, after which it reads nothing more. The peer still receives the close code. |
| Store format: empty lists and maps | `FormatNilSliceAsNull` writes `null` for a nil slice or map, such as a room with no `members`. | Writes `[]` or `{}`. | Rust has no nil slice. The Go server reads either form, so a database this port wrote opens in Go, and the other way round. Not client-visible. |
| Passkey attestation formats | go-webauthn verifies `packed` with an `x5c` chain, `tpm`, `android-key`, `android-safetynet`, `fido-u2f`, `apple` and `compound` statements, and registers the passkey if they check out | These registrations fail with "Passkey verification failed" | aprond requests no attestation, so a conforming client sends `none` or `packed` self attestation, which verify as in Go; only a client that ignores the preference sees the difference (docs/PORT.md) |
| `--apple.app-id` and `/.well-known/apple-app-site-association`, *extension* | No such flag. The path is 404, and `--static-dir` cannot serve it: `staticFS` refuses any path element that starts with a dot, and an extensionless JSON file would go out as `text/plain; charset=utf-8` (both checked against the Go `aprond`). | `--apple.app-id <team ID>.<bundle ID>`, repeatable (`[apple] app-id = [...]` in TOML), makes `GET` on that path answer `Content-Type: application/json` with `{"webcredentials":{"apps":[...]}}` and no redirect. Without the flag the path is unchanged. An ID that is not ten uppercase letters or digits, a dot, and a bundle ID stops `run` with `invalid --apple.app-id`. `--help` and `--print-config` end with an `Apple` group; a Go `aprond` loads a printed config whose `[apple]` table is empty, and stops on one that sets `app-id` with `unknown setting "apple.app-id"`. | A native iOS app can use a domain's passkeys only if that domain lists the app under `webcredentials`. A static directory is optional, so the server serves the file itself. |
| Account user_ids from a guest's passkey registration (§3.2, §3.3.3) | A guest that registers a passkey becomes the account in place and keeps its `guest_<n>` user_id, so Go never sends `user` with `old` (SERVER.md). The WebAuthn creation options name the user, `name` and `displayName` both, by the requested name, else the guest's name, else its user_id. | Follows apron-server-cloudflare (auth.ts `userIdSlug` and `candidateUserIdFor`, index.ts `handleAuth` and `guestLeaves`). The register `begin` on a guest's connection picks the new account's user_id from the requested `name`, normalized as any name is: lowercased, ASCII letters and digits kept, every other run one `_`, leading and trailing `_` dropped, cut to 16 characters; empty when it is `guest`, `bot` or `user` or starts with one of them and `_`. The id is that slug, `_`, and 4 digits, each a random u32 modulo 10, tried 8 times against every user_id assigned before, ignoring case, every room name, and every `Config.roles` holder; after 8 taken, or with no `name` or no slug, it is `u_` and 16 random bytes as unpadded base64url. The account's name is the requested one, else the guest's. The creation options give the id as `user.name` and the name as `user.displayName` (the id when there is no name). apron-web replaces both with the name typed for the account, when there is one, before the browser sees them (`labelledCreationOptions` in its `webauthn.ts`), so its passkeys are labelled as in Go. The id is not reserved at `begin`: `finish` claims it, and if another user took it meanwhile, `finish` is `invalid_params` (`identity already exists`) and the connection stays the guest. A verified `finish` answers `{you, token}` with the new user_id, its name, `roles: []` and its status. The guest is retired: its leave of each room it had joined, oldest room first, is logged and goes to the room's other members. The account then joins the same rooms in the same order, each join logged; the registering connection gets each as `room_update` `memberships` alone, then what follows a sign-in (§4.5): the statuses of those who share a room, and no mute. Everyone else in those rooms gets each join's `memberships`, the account's status with each join as with any join here, and then `user` `{new: <account>, old: {user_id, name}}`, the guest as recorded. The guest's messages and reactions keep its user_id, so the account cannot edit them; the rooms it created, its uploads and avatar, `ext`, chosen status, mutes, read cursors and push registrations go with the retired guest, and its user_id is never reissued. Unchanged: a passkey added to an account (passkey or email) keeps the user_id and the Go creation options; a guest adding an email address keeps `guest_<n>` in place, as in Go; a new email account is `user_<n>`; a registration on a connection not signed in is `denied`. Accounts made before this change keep their `guest_<n>` user_ids (docs/PORT.md, Migrating a guest_<n> account). | Owner decision, 2026-10-28: account user_ids follow the official servers, and where Go and Cloudflare differ, Cloudflare. Clients see a guest's registration as a sign-in to a new user: the `auth` result names another user_id, and the guest's messages are no longer the user's own. In Go's Playwright suite (`tools/interop/run.sh --project=desktop webauthn.spec.ts`), the two tests that expect the guest's user_id to survive registration fail at that check (webauthn.spec.ts:83 and :137); the other two pass, the passkey-label test among them because apron-web relabels the creation options. Where this differs from Cloudflare's: Cloudflare keeps guest memberships out of the log, so it sends no guest leaves, while this server logs them, as Go does, so the rooms' members get the guest's leaves before the account's joins, and a status with each join. rust-stdlib has no Unicode normalization (Display names row), so the slug skips Cloudflare's NFKD step: `Zoë Ångström` gives `zo_ngstr_m` here and `zoe_angstrom` there, and a fullwidth letter is a separator rather than its ASCII letter. The slug also refuses `user`, this server's email-account counter. The taken check ignores case and covers room names and role grants, where Cloudflare's compares user_ids exactly and covers renamed and purged ones, which this server has no commands for. A name over 64 runes is cut, as Go cuts any name, where Cloudflare answers `too_large`. A passkey added to an account keeps Go's creation options, where Cloudflare's `user.name` is the account's user_id. Cloudflare's guests only read and hold no mutes, pushes or avatars, so what is left with the guest here is what a Cloudflare guest could not have. Store: the account is an ordinary passkey `user` entry and its id an ordinary `used_ids` entry, so a Go `aprond` opens it as it opens any account; `tools/crossopen/run.sh` passed in both directions, the Rust-made `cross_open_<4 digits>` account resumed and signed in under Go. A Go `aprond` running on the same store still makes accounts in place. |
| `/invite-device <name>` command (§4.1, §3.2), *extension* | No such command: `/invite-device` is `Unknown command /invite-device; try /help`, and a passkey or email account has only the origin-bound session its own sign-in returned. | Follows apron-server-cloudflare's `/invite-device` (its SPEC.md, section 5, Devices). A passkey or email account runs `/invite-device <name>` and gets a `~private` markdown notice in the command's room, before the `{}` result, with a bearer token in a fenced code block, then a line `Or open this link on **<name>**, which signs you in there with any Apron app: <https://link.apron.chat/#server=wss://chat.example/ws&token=apron_device_…>` (an Appendix A.4 sign-in link, link.apron.chat SPEC.md section 2.1, with `server` and the token percent-encoded as Cloudflare's `apronLink` does: every byte but letters, digits and `-._~:/`), and the `auth` frame that uses it. The token is `apron_device_` plus 32 random bytes as unpadded base64url. Only its SHA-256 is kept, in a `device` store entry with the account, the name and when it was minted. `auth` with `scheme: "token"` and a device token signs in as the account from any origin or none; the result has `you` and no `token`. Device tokens do not expire. The name is 1 to 32 letters, digits, `_`, `.` or `-`, starting with a letter or digit; anything else, or other than one word, is `invalid_params`. An account holds at most 3 device tokens, one per name; a fourth name is `denied`, naming the three oldest first. The same name again mints a new token and revokes the old one: the old one no longer signs in, the account's other connections that signed in with it are signed out at once and get a connection-level `denied` error (`Device token replaced; sign in with the new one`) and close, so none of their requests runs as the account after the replacement, even one already read, and the push registrations made by connections signed in with it are deleted. Each registration's `push` store entry records that token's SHA-256, in hex, as a `device` member; one without it, stored before the member existed, is never deleted by a replacement. The asking connection stays open, even when it signed in with the replaced token, and then counts as signed in with the new one, so the next replacement closes it. A replacement undoes nothing else done with the old token: a passkey added with `register`, and the session token it returned, keep working, though a connection that signed in with the old token still closes after it got a session token. `/help` lists the command for accounts only. A guest gets `denied` (`Sign in with a passkey or email to use /invite-device`). A presented token that is unknown or revoked is `denied` (`This device token is not valid; get a new one with /invite-device on a signed-in device`). | A native client (the iOS app) cannot run the web client's passkey ceremony on every origin, so it signs in with a token another signed-in client issues, as §4.10 allows; matching the official server lets clients and docs give one instruction everywhere. Where this differs from Cloudflare's: Go has no bots and no `APRON_ADMIN_TOKEN` user, and its `admin` is a role on an ordinary account, so every passkey or email account may run the command, admins included, and the guest message names email too. A replaced token's connections close the way this server closes any connection, with an error frame and no close frame, rather than with close code 1008. The sign-in link names the `/ws` endpoint under the configured public URL (`--public-url`, or `https://` and the first `--tls.domain`), where Cloudflare names the URL the connection reached, so without a public URL the notice has no link line. A connection already signed in may present a device token, which switches it as a session token would, where Cloudflare answers `denied`. Go has no `/rename` or `/purge`, so a token ends only when its name is replaced. A Go `aprond` opening the same store loads only the entry kinds it knows: it ignores `device` entries, leaves them in place, and refuses device tokens. It skips the `device` member of a `push` entry and drops it when it next writes the entry. |
| `/invite-bot` command and bot users (§4.1, §3.2, §3.3), *extension* | No such command: `/invite-bot` is `Unknown command /invite-bot; try /help`. Go has no bots: every user is a guest, retired when its last connection closes, or a passkey or email account. | Follows apron-server-cloudflare's `/invite-bot`. A passkey or email account runs `/invite-bot`, which takes no arguments (any is `invalid_params`, `Usage: /invite-bot`). The first run makes the account's bot, the user `bot_<owner user_id>` named `Bot of <owner's name>` (the owner's user_id when it has no name), cut to the 64-rune name limit like any name. The bot has no credential and holds the roles `["bot"]`, and only those: `Config.roles` grants it nothing. It persists across connections and restarts as an account does, and joins `general` with a logged membership that the room's members receive as `room_update` `memberships`, as any join is. A later run renames the bot when the owner's name has changed since, which everyone who shares a room with it receives as a `user` notification. Every run mints a token, `apron_bot_` plus 32 random bytes as unpadded base64url, and replaces the bot's earlier one: the old one is deleted first, so a failure never leaves two, the bot's connections that signed in with it are signed out at once and get a connection-level `denied` error (`Bot token replaced; sign in with the new one`) and close, so none of their requests runs as the bot after the replacement, even one already read, and the bot's push registrations are deleted. Only the token's SHA-256 is kept, in a `bot` store entry keyed by its hex and holding `{bot, owner, created}`; the bot's `user` entry carries its owner in a `bot` member. The token goes only to the asking connection, in a `~private` markdown notice in the command's room before the `{}` result: it names the bot, as **<name>** followed by its user_id in code, says the token replaces any earlier one and that anyone who has it can post as the bot, then gives the token in a fenced code block and, after `If you're using an LLM, you can give it these instructions:`, a fenced block reading `Read https://github.com/shazow/apron/blob/main/PROTOCOL.md`, `Connect to <wss URL>` and `Auth using token scheme with this token: "<token>"`. `auth` with `scheme: "token"` and a bot token signs in as the bot from any origin or none; the result has `you`, with `roles: ["bot"]`, and no `token`. An unknown or replaced token is `denied` (`Bot token is not valid; its owner can get a new one with /invite-bot`). A bot is no account: it cannot run `/invite-bot` or `/invite-device` (`denied`, `Sign in with a passkey or email to use ...`), `/help` lists neither for it, and a passkey registration (`begin`) or an email proposal on a bot's connection is `denied` (`A bot signs in only with its token; it cannot add a passkey or an email address`). A bot's `me` with a name other than its own, after name normalization, is `denied` (`A bot is named after its owner, who can rename it with /invite-bot`); its own name, which the bot client sends on every connection, is no change, and its other fields change as anyone's do. `/help` lists `/invite-bot` for accounts only; a guest gets `denied` (`Sign in with a passkey or email to use /invite-bot`). | The owner tests bots against this server and needs a bot identity that outlives restarts, which a guest is not; matching the official server lets bot docs give one instruction everywhere. Where this differs from Cloudflare's: there is no 7-day sweep of idle bots, no `APRON_ADMIN_TOKEN` and no registration caps (one bot per account bounds the bots), and the notice has no `Say hello when you join` line, so bots do not greet rooms. A replaced token's connections close the way this server closes any connection, with an error frame and no close frame, rather than with close code 1008. The `Connect to` line names the `/ws` endpoint under the configured public URL (`--public-url`, or `https://` and the first `--tls.domain`), and reads `Connect to this server's WebSocket URL` without one. Should `bot_<owner>` already be held by someone else, a user_id taken before the prefix was reserved, `/invite-bot` is `denied` rather than reissuing it (§3.3). A Go `aprond` opening the same store skips the `bot` member of the bot's `user` entry and ignores `bot` entries, refusing bot tokens, but it takes the bot for a guest and retires it at start: it logs the bot's leaves and deletes its `user` entry. This server then drops the orphaned `bot` entry at its next start, and the bot's user_id, used, cannot be made again. |
| Requested `user_id` starting `bot_` (§3.2, Appendix A.3), *extension* | A guest or a new email account may request a user_id starting `bot_`, ignoring case, like any requestable one. | Such a request is not honored: the user gets the next `guest_<n>` or `user_<n>`, as for a requested `guest_` or `user_` id. | `/invite-bot` names each bot `bot_<owner user_id>`, so no other user may hold the prefix. A passkey registration's user_id is `<slug>_<4 digits>` or `u_…`, and the slug refuses `bot` (Account user_ids row), so no account gets the prefix either. |
| `--unfurl.enable` and `link` embeds (§4.8, §4.8.1), *extension, off by default* | No such flag. A message's URLs stay text, and the server never sets `og` on any embed but a finished upload. | With `--unfurl.enable` (`[unfurl] enable = true` in TOML), a saved message whose text gains http(s) URLs is posted and answered as before, and then unfurled in the background. The server reads the first 8 KiB of the text, and in it the first 32 distinct URLs, skipping, in `format: "markdown"`, those inside code spans and fenced code blocks. It leaves out URLs the previous snapshot's text already had (so a preview a user removed does not come back) and URLs an embed already links, and takes the first 3 that remain, so an edit that adds a URL gets that URL's preview. A save that keeps the text and format unchanged is not scanned. Each user gets 10 such URLs a minute, refilled evenly; at most 16 messages unfurl at once, and a message beyond that is not unfurled. Each page is fetched with `GET`, `User-Agent: Mozilla/5.0 (compatible; aprond/<version>; link preview; +https://github.com/iammatthias/apron-server-rust)`, a 5-second timeout over the whole exchange, at most 3 redirects, http and https only, no proxy, no kept-alive connections, and only to public addresses on ports 80 and 443: every dialed address, after each redirect too, must be on one of those ports and pass push's check (no loopback, private, link-local, CGNAT, documentation or other special-purpose ranges), checked on the address actually dialed, so a name resolves once and cannot be rebound. Only `text/html` and `application/xhtml+xml` answers are read, judged by their `Content-Type` before any of the body is, and only their first 512 KiB, as text: no script runs. The preview comes from the `og:title`, `og:description`, `og:site_name`, `og:image` (or `og:image:url`, `og:image:secure_url`) and `og:image:alt` meta tags, with `<title>` and the meta description as fallbacks. The `og:image` is downloaded under the same limits and kept only when it is declared `image/*`, is at most 2 MiB, and has the header of a PNG, JPEG, GIF or WebP of at most 8192 pixels a side and 40 megapixels in all (only the header is read, not the pixels); its `type` is the format the header reads as, whatever the site declared. It is then stored as an upload of the message. A page with no title, description or image gives no preview. Each URL's result is cached in memory, a preview for an hour and a failure for 5 minutes, at most 256 entries and 32 MiB of images. The message is then republished once, as for a finished upload (§4.8.3), with a `link` embed appended per preview whose URL its text still has: `{"embed_id", "kind": "link", "url": <the URL as posted>, "og": {"title", "description", "site_name", "image": {"url": <this server's /files/ URL>, "type", "width", "height", "alt"}}}`, absent members left out, within the 32-embed limit. A `link` embed is server-hosted (§4.8.2): a save that keeps its `embed_id` gets its `url` and `og` back from the server's records, and a save that drops it, a delete or a redaction deletes its image. Its image counts toward `--upload.max-storage-mb` but not toward a message's upload limit; when eviction takes the image, the whole `link` embed leaves the message, as an evicted upload does. A job is not persisted: a restart before it lands, or a message deleted or edited past its URLs meanwhile, leaves the message without the preview. `--help` and `--print-config` end with a `Link previews` group after `Apple`; a printed config always holds `[unfurl] enable = ...`, which a Go `aprond` refuses with `unknown setting "unfurl.enable"`. Store: a `link` embed is an ordinary `embed` entry. From Go's source (`persist.go` restores any `kind`, `handleFile` serves any finished embed with a file), a Go `aprond` opening the store restores the embed, serves its image and keeps its `og` on saves; `tools/crossopen/run.sh` does not cover embeds, so this is read, not run. | Clients load media only from the server's origin (§4.8.1), so a link can show a preview only if the server describes it and hosts its image, which the protocol allows (servers MAY publish a snapshot at any time, §3.5.3, and SHOULD set and host `og`). Off by default because it changes what the server does on the network: any user can make it request any public URL, which reveals the server's address to that site and spends its bandwidth, so the operator opts in, and without the flag the server stays identical to Go. |
| Frames from a closing connection | `closeWithError` (at shutdown and at the connection cap) queues the error and drops later outgoing frames, but the read loop keeps running the frames the client sends until the writer has drained and stopped the socket: a request in that window takes effect, a `message` is posted and broadcast to others, though its reply is dropped. | Once a connection-level error is queued, `process_frame` ignores every frame the connection sends, `auth` included, and an `auth` already read is `denied`. At shutdown, a request sent after the error was queued has no effect. | A replaced device or bot token must stop working at once (`/invite-device`, `/invite-bot`), and the close waits behind up to 128 queued batches, each written with a 10-second timeout, so a slow reader could keep acting on a revoked token for minutes. Every reply would be dropped anyway, so a client sees no difference except effects that, in Go, would follow a close it was already sent. |
| `aprond --help` width | go-flags wraps help to the terminal's width, read with an ioctl on standard input, and to 80 columns when standard input is not a terminal. | Always 80 columns. | rust-stdlib exposes no terminal-size call, and this crate forbids `unsafe`. Output is byte-identical to Go's whenever standard input is not a terminal. |
| TOML syntax errors | `Failed to load <path>: ` followed by BurntSushi/toml's message, such as `toml: line 1 (last key "x"): expected ...`. | `Failed to load <path>: toml: ` followed by the `toml` crate's message. | The decoder is a different library. Exit status and the `Failed to load` prefix match; `unknown setting` and `setting "...": ...` errors match exactly. |
| TOML dates in the config file | A date value reaches the option as Go's `time.Time.String()`, such as `1979-05-27 07:32:00 +0000 UTC`. | It reaches the option as its TOML text, such as `1979-05-27T07:32:00Z`. | No option takes a date; a date only matters for a string option, which then holds different text. |
| `/debug/pprof/` | Go's runtime profiles (heap, goroutine, CPU, trace). | The same routes from rust-stdlib's `net/http/pprof`; the index and `cmdline` work, and the runtime profiles, `profile` and `trace` answer that the profile is not available. | Rust has no Go runtime to profile. |
| `/debug/vars` | `cmdline` and `memstats`. | `cmdline` only. | rust-stdlib's `expvar` has no Go memory statistics to publish. |
| ACME certificates for clients without ECDSA | autocert issues an RSA certificate (cache name `<domain>+rsa`) for a ClientHello that lists no ECDSA signature scheme, P-256 curve, or ECDHE-ECDSA suite. | Every client gets the ECDSA P-256 certificate; a client without ECDSA fails the handshake. | Scope: the port issues ECDSA only. rust-stdlib-crypto has RSA, so the RSA path can be added; it serves only clients that support no ECDSA at all. A Go-written `+rsa` cache entry is ignored. |
| Non-ASCII TLS server names | autocert converts the SNI name with `idna.Lookup.ToASCII`. | A name that is not ASCII fails with `acme/autocert: server name contains invalid character`. | TLS carries A-labels (RFC 6066 §3), so a conforming client never sends one. |
| ACME failure text | When no challenge type is left, autocert's error names the authorization and domain only. | The same text, followed by ` (last: <the CA's error for the last challenge>)`. | The CA's reason is what an operator needs when reading the TLS handshake error in the log. |
| ACME time bounds | One five-minute context bounds `GetCertificate`, every request to the CA included. | Polling stops at a five-minute deadline and each request to the CA times out after 30 seconds. | rust-stdlib's HTTP client takes a timeout rather than a context. |
